# 1. Composer Framework

**Files:**
- `src/lib/composer/archetypes.ts` — Layer 1 (session shapes)
- `src/lib/composer/ingredients.ts` — Layer 2 (fillable content units)
- `src/lib/composer/composer.ts` — Layer 3 (scoring + slot filling)
- `src/lib/composer/index.ts` — barrel export
- `supabase/functions/compose-session/index.ts` — thin context wrapper (v1/v2 style)
- `supabase/functions/compose-session-v3/index.ts` — "Sankalpa Engine" (council + AI composer, 677 lines)

### 1.1 Layer 1 — Archetypes (`archetypes.ts`)

The core idea documented in the file header: *"Every session, regardless of ingredients, has one
of 7 shapes. The archetype is chosen by gate + energy + gap days + band — NEVER by the user."*
This is a **pure function module**, no I/O.

```ts
export type ArchetypeId =
  | "opening" | "inquiry" | "teaching" | "practice_deep"
  | "integration" | "release" | "micro";

export type SlotRole =
  | "settle" | "anchor" | "core" | "deepen" | "reflect" | "release" | "seal";

export interface ArchetypeSlot {
  role: SlotRole;
  share: number;                       // fraction of total session minutes
  accepts: Array<"practice" | "knowledge" | "reflection" | "micro_action">;
  practiceBias?: string[];
  depth?: "light" | "medium" | "deep";
}

export interface Archetype {
  id: ArchetypeId;
  label: string;
  description: string;
  preferredGates: GateId[];
  durationRangeMin: [number, number];
  energyFit: Array<"low" | "medium" | "high">;
  slots: ArchetypeSlot[];
  toneWords: string[];
}
```

The 7 archetypes are hard-coded in `ARCHETYPES: Record<ArchetypeId, Archetype>` (`archetypes.ts:56-160`),
each with an ordered slot template summing to ~1.0 share, e.g. `opening` = settle(0.25) → anchor(0.20)
→ seal(0.55); `practice_deep` = settle(0.10) → core(0.65) → deepen(0.15) → seal(0.10); `micro` is a
single core slot at share 1.0.

**Selection logic** — `selectArchetype(ctx: ArchetypeContext)` (`archetypes.ts:176-213`):

```ts
export interface ArchetypeContext {
  gate: GateId;
  energy: "low" | "medium" | "high";
  gapDays: number;
  timeBudgetMin: number;
  band: number;               // V-band 0-10
  preferred?: ArchetypeId;    // explicit user override
}
```

Priority order of rules:
1. `preferred` if set (still returns a `reason: "User preference"`).
2. `timeBudgetMin <= 3` → always `micro`.
3. `gapDays >= 4` → re-entry: `release` if night gate else `opening`.
4. `energy === "low"` → `release`/`integration`/`opening` depending on gate.
5. Gate-driven default switch: morning → `practice_deep` (if ≥15 min) else `opening`;
   midday → `inquiry` (if band≥3 and ≥8 min) else `teaching`; evening → `integration`;
   night → `release`.

Every branch returns `{ archetype, reason }` — the reason string is surfaced to the UI/AI as an
explanation, not just used internally.

### 1.2 Layer 2 — Ingredients (`ingredients.ts`)

Ingredients are the *fillable units* dropped into archetype slots. Rather than re-implement a
practice catalog, this layer **wraps** the existing `MODE_REGISTRY` from `@/lib/sutra/modeRegistry`
as `practice` ingredients, and hand-authors small libraries for `knowledge`, `reflection`, and
`micro_action` kinds (candidates for a future DB move, per the file header).

```ts
export type IngredientKind = "practice" | "knowledge" | "reflection" | "micro_action";
export type Depth = "light" | "medium" | "deep";
export type Energy = "low" | "medium" | "high";
export type Gate = "morning" | "midday" | "evening" | "night";

export interface Ingredient {
  id: string;
  kind: IngredientKind;
  label: string;
  summary?: string;
  defaultMinutes: number;
  practice?: Practice;            // only for kind="practice"
  loopTargets?: string[];         // loop IDs this ingredient addresses (e.g. VAL001)
  bandRange?: [number, number];   // inclusive V-band window
  energyFit?: Energy[];
  gateFit?: Gate[];
  depth: Depth;
  route?: string;                 // deep link for practice ingredients
  body?: string;                  // static copy for knowledge/reflection/micro cards
  icon?: string;
}
```

`PRACTICE_INGREDIENTS` (`ingredients.ts:50-60`) is generated by mapping every entry of
`MODE_REGISTRY` into an `Ingredient`, deriving `depth` from `defaultDurationSec`
(≥600s → deep, ≥240s → medium, else light) and calling `m.route({})` for the deep link.
`KNOWLEDGE_INGREDIENTS` (4 seed teachings, e.g. "The Guest House"/Rumi, "Witness vs Thinker"),
`REFLECTION_INGREDIENTS` (5 gate-tagged prompts), and `MICRO_ACTION_INGREDIENTS` (5 quotes/mantras/
presence cards) are hand-authored arrays. `ALL_INGREDIENTS` concatenates all four; `getIngredientById`
is a simple lookup helper.

### 1.3 Layer 3 — Composer (`composer.ts`)

Pure function `composeSession(ctx: ComposerContext): ComposedSession` — given full context, it:

1. Calls `selectArchetype(ctx)` to lock the shape.
2. For each archetype slot, filters `ALL_INGREDIENTS` by `eligibleFor(slot, ing, ctx)`
   (kind must be in `slot.accepts`; band/energy/gate must intersect the ingredient's constraints if
   set) and not already used in this session.
3. Scores every eligible candidate via `scoreIngredient(ing, slot, ctx)` — a weighted sum:

```ts
const W = {
  loopMatch: 3, practiceLevelFit: 2, gateAlignment: 2, freshness: 1.5,
  energyFit: 1, bandFit: 1, slotBias: 2.5, repetitionPenalty: -4,
} as const;
```

   Components: loop-target overlap with `ctx.activeLoops` (×hits); practice-level fit (rewards
   matching ingredient depth to the user's current practice level, penalized by `|level - want|`
   where deep wants level 3, medium wants 1, light wants 0); gate alignment; freshness (bonus if
   `ing.id` not in `ctx.recentIngredientIds`, else a strong `-4` repetition penalty); energy fit;
   band-range presence bonus; and slot-specific `practiceBias`/`depth` matching bonuses.
4. Picks the highest-scoring ingredient per slot, marks it "used", and computes `minutes` from
   `timeBudgetMin * slot.share`, then **renormalizes** minutes across all filled slots so the total
   exactly equals `ctx.timeBudgetMin` (last slot absorbs rounding remainder).

```ts
export interface ComposerContext extends ArchetypeContext {
  activeLoops: string[];
  practiceLevels: Partial<Record<Practice, number>>;
  recentIngredientIds: string[];
}
export interface ComposedSlot {
  role: ArchetypeSlot["role"]; roleLabel: string; ingredient: Ingredient;
  minutes: number; score: number; reason: string;
}
export interface ComposedSession {
  archetypeId: Archetype["id"]; archetypeLabel: string; archetypeReason: string;
  toneWords: string[]; totalMinutes: number; slots: ComposedSlot[];
}
```

`composeTitle(session, gate)` builds a human title like `"Curious Opening"` from the first tone
word plus a gate-derived suffix (Opening/Settling/Release/Pause).

**Important:** this client-side pure-composer module (`src/lib/composer/*`) is NOT directly called
by `compose-session-v3` (the AI-driven edge function reimplements its own archetype/step logic in
Deno). It is consumed by `useComposedSession()` (client preview/"What to expect" card) and by the
legacy `compose-session` edge function. The *runtime* deterministic fallback inside
`ConsciousnessOrchestrator` now imports the canonical `supabase/functions/_shared/composer.ts`
through the `src/supabase/_shared/composer.ts` re-export, so client and server share one
implementation. Both share the same conceptual vocabulary (archetype, slot, ingredient/step) and
the same underlying `getUserContext()` substrate.

### 1.4 Edge function: `compose-session` (thin wrapper)

**File:** `supabase/functions/compose-session/index.ts` (68 lines)

Literally described in its own header comment: *"Returns the full user-context snapshot +
composer input. Thin wrapper around getUserContext() — the single source of truth."*

Contract:
- **Auth:** requires `Authorization` header; resolves `user` via anon-key client.
- **Body:** `{ timeBudgetMin?, energy?, hour?, gate?, preferred? }`.
- Calls `getUserContext(supabase, user.id, { timeBudgetMin, energy, hour, gate })`.
- Builds a back-compat `ctx` object shaped like `ComposerContext` (gate, energy, gapDays,
  timeBudgetMin, band — rounded from `vLevelCurrent`/`overallBand`, activeLoops as `recentLoopIds`,
  practiceLevels via `practiceLevelsMap()`, recentIngredientIds, preferred).
- **Response:** `{ ok: true, ctx, userContext: userCtx }` — i.e. it does not itself call
  `composeSession()`; it hands back the raw materials for a caller (client or another function) to
  compose with.

### 1.5 Edge function: `compose-session-v3` — the "Sankalpa Engine"

**File:** `supabase/functions/compose-session-v3/index.ts` (677 lines) — by far the most complex
function in the report. Header comment summarizes the pipeline:

```
Parallel reader  →  3-LLM Council (fast)  →  Composer (main)
                 →  Safety + write session_spine
```

It honors `userCtx.identity.aiMode` ('fast' Groq vs 'premium' OpenAI) via `aiGatewayFetch` for
every AI call.

**Current client wiring (verified 2026-11-14):** there is no `sankalpaV3` feature flag anywhere in
the codebase — the docstring's "flag off" path no longer exists. `startGenerativeSession()`
(`src/lib/session-shell/api.ts`) invokes `compose-session-v3` unconditionally; if the invoke or the
plan validation fails it falls through to the in-process `ConsciousnessOrchestrator`, and
`useHomeSessions` keeps a third, purely local `startGenerativeSessionLocalFallback` plan. The
downgrade is recorded on `plan._meta.fallbackReason` and rendered in the session intro card, so it
is no longer silent.

**Contract:**
- Request: `{ timeBudgetMin?, energy?, gate?, intent? }`, requires auth.
- Response: `{ ok, plan: { id, intent, intro, steps[] }, spineId, council, chakraFocus,
  whyForYouCount, novelty[], memoryCallback, whisperConsumed, nextWhisper, themeId, elapsedMs, aiMode }`.

**Step model:**

```ts
type StepKind = "wisdom-read" | "breathwork" | "journal" | "micro-act"
  | "reflection" | "guide-chat" | "practice" | "temple-chat" | "witness";

interface Step {
  kind: StepKind; title: string; prompt?: string; params?: Record<string, unknown>;
  est_minutes: number; whyForYou?: string; signalRef?: string;
}
interface Plan { id: string; intent: string; intro: string; steps: Step[]; }
```

**14 archetypes with activation conditions** (`ARCHETYPE_SPEC`, lines 49-64) — a superset far
richer than the client-side 7-archetype model: `Settling`, `Confrontation`, `Reconciliation`,
`Shadow Mirror`, `Stuck-Loop Break`, `Lineage Initiation`, `Re-entry`, `Celebration`, `Dissolution`,
`Witness Deepening`, `Inquiry Spiral`, `Devotional`, `Karmic Action`, `Dark Night Hold`. Each has a
`tagline` and an `activate` condition string (fed to the LLM as instructions, not code-evaluated —
the LLM decides which condition "fires").

**Voice lineage** — three inner voices (`head`/`heart`/`gut`) are each mapped to a yogic path and a
list of historical masters (`VOICE_LINEAGE`, lines 68-72): head→Jnana (Ramana, Krishnamurti,
Nisargadatta, Shankara), heart→Bhakti (Rumi, Meera, Ramakrishna, Hafiz), gut→Karma/Raja
(Adiyogi/Shiva, Patanjali, Buddha, Lao Tzu).

**Pipeline, step by step:**

1. **Auth + admin clients** — user client (anon key + auth header) and `admin` (service role).
2. **Parallel READ layer** (`Promise.all`, lines 115-144):
   - `getUserContext()` for the full snapshot.
   - `buildLongTermMemoryBlock()` (from `_shared/long-term-memory.ts`) — semantic memory recall
     block (see §6).
   - Previous `session_spine` row (last completed session's archetype/lead/loop/dimension/chakra +
     `final_user_sentence`) for a "memory-graph callback."
   - Unconsumed `future_self_whispers` row left by a previous session for the user's future self.
   - Latest `daily_themes` row (the "living theme" arc for today).
   - Last 30 quality-scored `session_spine` rows for **adaptive archetype/voice history**.
3. **Adaptive history block** (lines 151-177) — aggregates archetype and lead-master average
   quality scores from history, builds `top`/`bottom` resonance lists, and folds this into
   `adaptiveBlock`, explicitly instructed to the LLM as *"soft bias only — do NOT pick a high-resonance
   archetype if its activation rule does not fire."*
4. **Signal assembly** (lines 183-232) — builds a `signals` object (vLevel, journeyDay,
   chittaVritti, dimensions, dimensionBands, activeLoops, yogaPathAffinity, witness stats, gate,
   energy, timeBudgetMin, gapDays), computes `starvedDim` (lowest-scoring dimension today), builds
   a `practiceMatrix` signal via `_shared/practiceMatrix.ts` (`buildPracticeMatrixSignal`), detects
   a blocked chakra via `_shared/chakraEngine.ts` (`detectBlockedChakra`), and resolves human-
   readable loop names via `_shared/loopMap.ts` (`loopName`).
5. **COUNCIL LAYER** — three parallel fast LLM calls (`voiceCall("head"|"heart"|"gut")`,
   lines 241-271), each constrained to ONE sentence ≤24 words in second person, given the shared
   signals block. A **synthesizer** call (lines 273-323) then picks exactly one `lead` voice and
   one `archetype` from the 14-item menu, informed by activation rules + adaptive history +
   deepest-need tie-break ordering (`Dark Night > Shadow Mirror > Confrontation > ... > Settling`).
   Falls back to `{lead:"gut", archetype:"Settling"}` on any failure.
6. **COMPOSITION LAYER (main call)** — `stepBudget = clamp(3,7, round(timeBudgetMin/3))`. The
   system prompt (`composerSys`, lines 330-360) locks the archetype, names the lead voice's
   lineage, enforces per-archetype step-shape rules (e.g. Dark Night Hold: no "do" verbs, only
   breath/witness/soft reflection; Karmic Action: exactly one micro-act step), and a **"practice
   grammar"**: every step must instantiate one concrete `(family × focus × level)` cell from
   `{observation, self_inquiry, breath_awareness, witnessing, body_awareness, bhakti, karma, jnana,
   raja, kriya, tantra}`, never jumping more than +1 level above the user's current level for that
   family. Every step requires a `whyForYou` (must reference a **named** signal: loop name,
   dimension, chakra, practice level, memory line, or council voice — explicitly bans vague
   "because it's good for you" reasons) and a `signalRef` id (e.g. `loop:VAL003`, `dim:emotion`,
   `chakra:throat`, `practice:witnessing:L2`, `memory:14d`).
7. **T4 memory-graph callback + whisper + living theme** (lines 362-403) — builds `callbackBlock`
   referencing the previous session (hours-ago, archetype, loop, dimension, chakra, closing
   sentence), the future-self whisper (if any, to be woven not quoted), and the living theme's
   current sub-angle/depth — with explicit **INTRO RULES**: intro must open with a memory-graph
   callback sentence if history exists, fold in the whisper's essence as sentence 2, and close by
   signaling how today deepens the living theme; capped at 3 sentences total.
8. **Composer AI call** (`tier:main`, JSON mode) parses into `Plan`; cleans/clamps each step
   (`title` ≤120 chars, `prompt` ≤1200, `est_minutes` clamped 1-15, `whyForYou` ≤280,
   `signalRef` ≤80). If parsing fails at any point, a **hard-coded 3-step safety fallback plan**
   is used (breathwork → witness → reflection) so the function never returns an empty plan.
9. **T3 Novelty filter** (lines 468-541) — embeds every step's `title+prompt` via `embedText()`
   and does a `match_user_memories` RPC search restricted to `source_type = "session_step"`;
   flags any step whose max similarity to prior steps > 0.85. Flagged steps trigger a **one-shot
   regeneration** AI call (`novelty-repair`) that rewrites only the flagged indices, preserving
   kind/duration/archetype, then re-embeds the replacements.
10. **WRITE layer** (lines 543-586) — inserts a `session_spine` row capturing archetype, reason,
    lead master, council voices, primary/secondary loop ids, primary dimension, chakra focus,
    `why_for_you` array, `graph_edges` (loop/dimension/chakra/master nodes), full `composed_signals`,
    and `ai_mode`. Fire-and-forget: persists step embeddings into `user_memory_vectors` tagged with
    `[kind, archetype, lead]` for future novelty checks.
11. **T4 post-write side effects** (lines 588-653, all fire-and-forget) — marks the consumed
    whisper, generates a **new future-self whisper** (one sentence, ≤22 words, tone enum
    `tender|fierce|playful|grave|grateful`) referencing what was just composed, and — if a living
    theme is active — POSTs to `evolve-theme` with the spine id, archetype, lead master, and
    primary loop/dimension to advance the day's theme arc.
12. Returns the full response payload described above.

This function is a genuinely layered pipeline: deterministic reads → parallel small LLM voices →
one synthesizing LLM decision → one large generative LLM composition → embedding-based novelty
QA/repair → durable graph-shaped persistence → fire-and-forget continuity generation for the *next*
session. It is the clearest example in the codebase of "engine chaining."
